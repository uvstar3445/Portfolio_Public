AES-128 FPGA coprocessor

ENGG*4560 · Embedded System Design · Team project

Connecting a Linux C application to FPGA encryption hardware through a memory-mapped interface, with CBC test results documented on the board.

  • C
  • Verilog
  • Linux
  • FPGA
  • Quartus Prime
  • Platform Designer
  • Memory-mapped I/O
  • Hardware-software integration

The challenge

Make a 32-bit software interface work with a 128-bit encryption core. The project brought together the ARM Hard Processor System (HPS), a custom APB wrapper, and an AES core on the FPGA.

My contribution

  • Developed embedded C applications for communication between software and hardware.
  • Compiled and ran Linux applications that exchanged data with hardware registers.
  • Tested peripheral control and debugged communication behaviour.

Completed with a three-person team. The architecture, screenshots, and results below document our shared final project.

How the pieces connect

A C application running on the ARM processor accesses the FPGA peripheral through the lightweight HPS-to-FPGA bridge. The APB wrapper exposes the registers used to exchange data with the AES core.

  1. Prepare the input. Represent each 128-bit value as four 32-bit words for register access.
  2. Start the operation. Use control and status signalling to coordinate the software with the hardware state machine.
  3. Read and compare. Retrieve the ciphertext words and compare the result with a known reference.

Making the interface work

The custom component exposes address, read/write data, select, enable, and ready signals, along with clock and reset connections.

The wrapper groups 32-bit register values for the 128-bit AES core. Its state machine coordinates waiting, loading, encryption, and completion so software can determine when to read the result.

Engineering trade-offs

The report identifies the combinational AES path and repeated register transfers as design constraints. DMA and changes to the core’s timing structure are possible follow-up work, rather than features demonstrated here.

What I took from it

This project made the hardware-software boundary feel much more real to me. Even when the encryption logic is correct, the system still fails if the software and hardware disagree on word ordering, register access, or when a result is ready, so I learned to treat the interface itself as part of the design rather than just the connection between two pieces.

Project scope

This was a three-person embedded-systems team project. The page presents functional integration and reference-vector test evidence; the final report does not provide measured throughput or a security evaluation, so those are not claimed here.
